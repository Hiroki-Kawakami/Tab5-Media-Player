# H.264 decoder

`components/h264_dec` is a Constrained Baseline decoder written for this player
from ITU-T H.264. It is plain C with no ESP-IDF dependency apart from an
optional PIE assembly file, and it builds and runs on the host. How the player
drives it is in [`playback.md`](playback.md#h264-playback).

## Why not `espressif/esp_h264`

Earlier projects (Tab5-Screen-Streamer, Tab5-SDR) used it and hit three walls:

- Its software decoder (tinyh264) is a prebuilt archive that allocates its own
  memory, so nothing about where its working set lives can be chosen. It
  decoded 720x1280 at 9-10 fps and 1280x720 at about 3 fps, and most of that
  time was copying reference blocks out of PSRAM.
- It only outputs planar I420. PPA's YUV420 input is Espressif's packed
  `O_UYY_E_VYY`, so every frame had to be repacked on the CPU before scaling.
- Its PIE assembly is not on the decode path at all.

## Scope

Progressive Main and High profile, 4:2:0, 8-bit. That covers what ffmpeg and
YouTube produce by default, which is why the scope grew past the Constrained
Baseline it started as: a 360p MP4 picked up from the internet is Main (CABAC,
B slices) or High (also the 8x8 transform), never Baseline.

Accepted: CAVLC and CABAC, I/P/B slices, both direct modes, explicit and
implicit weighted prediction, the 8x8 transform and Intra 8x8, scaling
matrices, all three POC types, output reordering, multiple slices, multiple and
long-term references, MMCO, reference list modification, frame_num gaps,
constrained intra prediction, redundant pictures (skipped), I_PCM.

Rejected: interlace and MBAFF, FMO (slice groups), SP/SI slices, 4:2:2, 4:4:4
and bit depths above 8. Data partitioning never reaches the decoder because
Extended profile is refused in the SPS.

## Memory

**Reference pictures are stored in PPA's packed layout.** Each DPB frame is a
`O_UYY_E_VYY` buffer in PSRAM, the same bytes PPA scales from. A decoded frame
is therefore written to PSRAM exactly once and presented without conversion,
and a redraw after a rotation is one PPA call on the held frame. The price is
that motion compensation cannot read references as planes; it unpacks what it
needs (below).

- **The frames are one PSRAM allocation per stream** (`dpb + 1 + held`), made
  when an SPS is activated. `dpb` is the VUI's `max_dec_frame_buffering` when
  the stream states it and otherwise what the level allows for the picture
  size, so a stream that reorders heavily still has somewhere to put the
  pictures it is holding back. `frame_budget_bytes` caps the result: at 720p
  the level would allow up to 16 frames, which does not fit next to the
  framebuffers. There is 64 bytes of slack at the end because the 48-byte
  unpack kernel can read past the last row.
- **Reference pictures also carry their motion**, in a second PSRAM block, for
  B direct prediction to read as the colocated picture. Four entries per
  macroblock with `direct_8x8_inference_flag` (the usual case) and sixteen
  without, 6 bytes each: the motion vector, the reference index inside the
  colocated slice's list and the pool index of the picture it pointed at. The
  pool index is what maps a colocated reference onto the current list 0, and it
  works because a picture the colocated one referenced is still in the DPB. The
  worker writes a row of it next to the pixels, so the decoding core never
  touches it.
- **A stream that changes size while pictures are held stops with an error.**
  Reallocating would free a frame the presenter is about to draw, and the
  presenter always holds the picture on screen. Files that change size
  mid-stream are rare enough not to justify deferred frees. A new SPS that only
  differs in fields that do not affect the layout (a per-picture PPS/SPS pair is
  common) keeps the pool, because dropping it would throw away the pictures
  waiting to be output.

**The shared 240 KiB SRAM is the decoder's work arena.** While a video plays
the main LVGL display is hidden, so the two strip buffers MJPEG uses are free
(see [`architecture.md`](architecture.md#shared-sram-buffer)). The decoder
takes the whole block as one bump allocator, 16-byte aligned for PIE (sizes are
approximate):

| what | 640 wide | 1280 wide |
|---|---|---|
| VLC tables | ~5 KB | ~5 KB |
| bitstream chunk (de-escaped RBSP) | 16 KB | 16 KB |
| packed scratch row (16 lines) | 15 KB | 31 KB |
| MC temporaries, top line, coefficients | ~4 KB | ~6 KB |
| CABAC contexts, level scales | ~3 KB | ~3 KB |
| reference window | 88 KB | none |
| row slots (16+4 luma lines, 8+2 chroma, MB info) | 26-29 KB each, 3-4 | 50-56 KB each, 3 |

**Per-macroblock info is sized per stream.** A row slot carries an `mbinfo_t`
per macroblock: what deblocking and prediction need from the neighbours. The
list 1 half of it (motion vectors, reference indices and the CABAC mvd edges) is
only allocated when the stream may contain B slices, which is decided from the
profile in the SPS, and `dec->mb_stride` is the resulting element size. That is
what keeps a Baseline stream at four row slots at 360p; Main and High get three.

Everything that is hot and not a whole picture lives here: the macroblock
being reconstructed, its neighbours, the deblocking lines, the RBSP bytes
(de-escaped 16 KB at a time, so the reader never touches the PSRAM packet
per bit) and, at 360p, the part of the reference frame motion compensation
reads.

**Code stays in flash.** Mapping the hot objects to IRAM with a linker
fragment made the image fail to boot: with the whole archive the
`esp_hosted` SDIO driver could no longer allocate its DMA pool
(`sdio_mempool_create` assert, boot loop), and with only the six smallest hot
files the board reset during PSRAM timing tuning. The shared array is `.bss`
and ESP-IDF's default memory protection keeps data memory non-executable, so
it cannot hold code either. Revisit only together with
the internal-RAM budget (turning off `esp_hosted` would free it, but WiFi is
not this component's decision).

## Output order

Pictures are decoded in bitstream order and handed out in display order, so the
API is a pull: `h264_dec_decode()` takes an access unit and a caller tag,
`h264_dec_output()` returns whichever picture is ready next, and
`h264_dec_drain()` releases what is left at the end of a stream. The tag comes
back with the picture, which is how the player keeps a due time attached to a
frame across the reordering.

- **A picture is released when holding it back can no longer change the order.**
  That is the bumping process of the standard: output the lowest picture order
  count once more than `num_reorder_frames` are waiting, or once the DPB has no
  room. Waiting frames occupy pool slots, so "no room" is measured in free
  slots rather than a frame count: nothing else can free a slot, because a
  picture is only reusable after the app has taken it and released it.
- **After the first two outputs the wait usually disappears.** The decoder
  learns the smallest positive gap between successive output POCs and, as long
  as the next waiting picture is within one such step of the last one it gave
  out, hands it over immediately. A stream that states `num_reorder_frames` in
  its VUI (x264 does) therefore only pays the delay the encoder asked for, and
  one that does not still starts correctly rather than guessing zero.
- **IDRs and MMCO 5 start a new epoch.** POC restarts at zero there, so a plain
  POC comparison would interleave the new sequence with the old one. Frames
  carry an epoch counter and sort by (epoch, POC). Output does not restart early
  at an epoch boundary either: a stream whose first pictures have negative POCs
  (`CVWP2_TOSHIBA_E` does) would otherwise show its I picture first.
- **Starting at a non-IDR I picture drops the leading pictures.** After a seek
  the decoder records the POC of the picture it restarted on and does not output
  anything below it; those pictures reference something that was never decoded.

## CABAC

The arithmetic decoder reads its bits through the same `bits_t` reader as
everything else, one bit per renormalisation. That is not the fastest possible
arrangement, but it means the 16 KB de-escaping refill keeps working underneath
it: the engine holds no pointer of its own, so a refill that moves the buffer is
invisible to it. Two consequences are worth knowing:

- **CABAC reads past the end of the slice.** The engine has nine bits of the
  bitstream inside `codIOffset` before the first bin and one more per
  renormalisation, so at the end of a slice it has consumed the
  `rbsp_stop_one_bit` and beyond. `bits_overrun()` therefore reports an error
  for every CABAC slice; the macroblock layer uses `bits_past_buffer()`, which
  only fires when the reader has run off the buffer itself. Getting this wrong
  costs the last macroblock of every picture.
- **I_PCM restarts the engine, not the contexts.** The samples are read
  byte-aligned from where the engine's reader stands, and only `codIRange` and
  `codIOffset` are re-initialised afterwards (spec 9.3.1.2). The macroblock also
  has to leave the neighbour state a PCM block implies: all coefficients
  non-zero, chroma `cbp` 2, the DC flags set.

Contexts are the spec's tables (`src/cabac_tables.c`), 460 of them, initialised
from the slice QP and `cabac_init_idc`. The neighbour-dependent context
increments need state the CAVLC path never kept: the coded block pattern and DC
coded-block flags of the two neighbours, whether they were skipped, direct or
`I_NxN`, their chroma prediction mode, and the absolute mvd of the blocks along
their edges. All of that lives in `mbinfo_t`, except the current macroblock's
own mvd, which is a scratch array in the parsing context and copied to the
edges when the macroblock ends. Skipped and intra macroblocks have to clear
those edges, or a later macroblock reads motion differences that never existed.

## B slices

- **Both reference lists are stored per macroblock**, because deblocking has to
  compare them: a boundary is smooth only when the two sides use the same
  pictures (in either pairing) with close vectors.
- **Direct macroblocks predict the whole macroblock at once when they can.**
  Spatial direct derives one reference and one vector per list for the
  macroblock and then only zeroes a block's vector where the colocated block was
  still; temporal direct scales the colocated vector per block. Both usually
  come out the same for all four 8x8 blocks, and predicting 16x16 once instead
  of four times (twice each, for two lists) is worth measuring: on the device it
  took a 360p High clip from 58 to 36 ms per frame, because every motion
  compensation call pays for a reference fetch and the filters process 16
  samples per row whatever the block width.
- **Bi-prediction goes through SRAM temporaries.** Each list is predicted into
  a 16-wide scratch buffer and combined afterwards, with the implicit weights
  when `weighted_bipred_idc` is 2, the explicit tables when it is 1, and a plain
  average otherwise. Implicit weights of 32/32 are the common case and take the
  average path, which is the PIE kernel.

## The row pipeline

Reconstruction, deblocking and packing are split by macroblock row, and the
deblocking half runs on the other core (`h264_post`, core 1).

- **The decoder core** parses and reconstructs a row into a slot. Before
  handing the slot over it copies the row's unfiltered bottom line into a
  private top-line buffer, because intra prediction must see samples from
  before the deblocking filter. It then takes a free slot for the next row and
  copies the top line into that slot's line -1.
- **The worker** deblocks row r in its slot. The top edge filter touches the
  bottom lines of row r-1, which live in another slot, so their last four luma
  and two chroma lines are copied into row r's lines above 0, filtered there
  and copied back. Row r-1 is then final: it is packed into the SRAM scratch
  (PIE) and written to the PSRAM frame in one `memcpy`, and its slot is freed.
- **Slots are a ring of at least three**: the worker holds r-1 and r while the
  decoder fills r+1. More slots only let the worker fall further behind. The
  decoder waits for the last row of a picture before starting the next one,
  because that picture becomes the reference.
- **The component knows nothing about FreeRTOS.** Counting semaphores and task
  creation come in through `h264_dec_threads_t`
  (`app/video/h264_threads.cpp`); without them every job runs inline. The host
  test tool supplies pthread versions.

Measured on the device with the post stage on core 1, the decoder core spends
under 5% waiting for it on a typical clip.

## Motion compensation

**References are unpacked into SRAM before filtering.** A 16x16 block needs a
21x21 region; one `vunzipt`+`vzip` per 48 packed bytes yields 32 luma samples,
and a batched kernel does all rows in one call. The 6-tap and bilinear filters
then only read SRAM.

**At 360p a window of the reference is kept in SRAM as planes.** Fetching
from PSRAM costs 4000-5500 cycles per block however the copy is written, which
was most of the motion compensation time. The window holds the
rows around the current macroblock row of the first reference in list 0:

- **It is a 64-row ring whose first 22 rows are mirrored after the end**, so
  any 21-row span is contiguous and the filters read it in place with no fetch
  at all. Each row has 32 bytes of padding: the unpack kernel writes whole
  16-pair blocks, and without padding the overflow of the newest row landed on
  the oldest valid row exactly when the ring was full (a few wrong samples near
  the left edge, found by the regression clips).
- **The margin is 16 rows above and below.** With 24 the span filled the whole
  ring and nothing could be prepared ahead, so the decoder waited for every
  row.
- **Both cores fill it.** Rows are claimed with a compare-and-swap, the worker
  fills ahead of the decoder, and the decoder fills rows itself instead of
  sleeping when it would otherwise wait for a slot. `win_busy` is published
  before a claim, not after, so the decoder never reads a row the worker has
  claimed but not written.
- **Only list 0 index 0 is windowed.** The block does not fit twice. x264's
  default of three references sends about a third of the blocks elsewhere,
  and those still fetch from PSRAM.
- **Not at 720p.** The window would need 171 KB.

**Kernels write 16 samples even for narrower blocks.** Everything to the
right of a partition in the same rows is predicted later in z-order, and the
residual is added after all partitions, so the overwritten samples are always
rewritten. Row buffers have 32 luma and 16 chroma samples of margin for the
last macroblock. A full-pel block at an odd x is the one exception: its unpack
starts one sample to the left, so that sample is saved and restored.

## PIE

`src/kernels_p4.S` has PIE versions of the 6-tap filter (rounded and
intermediate), averaging, chroma bilinear, pack and unpack; `src/kernels_c.c`
has the C versions the host uses. Both write the same bytes, including the
extra samples of narrow blocks, so the host checks the device's memory
behaviour too. Facts that shaped them, measured on this board with IDF v6.1:

- **Several PIE tasks on one core are fine on v6.1**, unlike what Tab5-SDR saw
  on v6.0.2. What hangs is a PIE task whose stack is in LP RAM: the lazy save
  stores 128-bit vectors on the stack, and RTC RAM (enabled as heap here) can
  not take them. PIE tasks (`video_decoder`, `h264_post`, the bench) are
  created with `MALLOC_CAP_SIMD` stacks through `h264_create_task()`.
- **Ask for `MALLOC_CAP_SIMD` alone.** The P4 heap matches caps one priority
  level at a time, and `RETENT_RAM`, where most of the free internal memory
  is, lists SIMD and INTERNAL on different levels. `SIMD | INTERNAL` therefore
  only matches the small `RAM` regions, which are used up by the time the
  player opens, and the presenter tasks silently failed to start. `SIMD` alone
  takes `RETENT_RAM`, then `RAM`, then PSRAM, and never RTC RAM or SPM.
- **Nothing else in the firmware uses PIE**, including the prebuilt audio
  codecs and the ROM `memcpy`.
- **`CFG` is global and not saved per task.** `h264_k_prepare()` sets the
  misaligned-load/store bits with a read-modify-write and SAR to 0 at the start
  of every decode call and in the worker; the kernels do not touch it.
  Misaligned loads with the bit clear silently read from the address rounded
  down.
- **`vmul.s16` saturates**; the filters are arranged so no product exceeds
  16 bits (`20(c+d) - 5(b+e) = 5(4(c+d) - (b+e))`, `8A + fx(B-A)`).
- **`vsld.16` with a negative per-lane count is an arithmetic right shift**
  that rounds like C `>>` under the default rounding mode, so `+16 >> 5`
  matches exactly.
- **`vunzipt.8`/`vzipt.8` split and join `C Y Y` triplets**, which is what
  made the packed DPB cheap.

## Deblocking

Most macroblocks in real video are skipped or have one motion vector and no
coefficients. `mbinfo_t` carries `uniform` and a luma non-zero mask, so such a
macroblock skips its internal edges without computing a single boundary
strength, and an edge between two of them is decided by one motion
comparison. On a typical clip that cut the deblocking time by more than half.
`uniform` is set for any macroblock with one motion vector per list over the
whole macroblock, bi-predicted and merged direct ones included, which is why B
pictures cost less in deblocking than they otherwise would.

With the 8x8 transform the internal edges at four and twelve samples are not
filtered, and a non-zero 8x8 block marks all four of its 4x4 blocks in the
non-zero mask, because that is what decides boundary strength 2.

## Verifying

The decoder is deterministic, so every output is compared byte for byte with
ffmpeg.

```sh
nix develop -c cmake -S components/h264_dec/test -B components/h264_dec/test/build -G Ninja
nix develop -c cmake --build components/h264_dec/test/build
components/h264_dec/test/build/h264_dec_test clip.h264 out.yuv   # cropped I420
nix develop -c ffmpeg -i clip.h264 -fps_mode passthrough -f rawvideo -pix_fmt yuv420p ref.yuv
cmp out.yuv ref.yuv
```

- **Environment switches**: `H264_THREADS=1` uses the two-stage pipeline with
  pthreads, `H264_HASH=1` prints an FNV-1a of every packed frame (the same
  format the device bench prints), `H264_LOOPS=n` repeats the file for
  profiling, `H264_VERBOSE=1` prints each access unit's result.
- **Sanitizers**: configure a second build with `-DH264_SANITIZE=ON
  -DCMAKE_C_COMPILER=/usr/bin/clang` for UBSan. ASan hangs in its own start-up
  on this macOS; ThreadSanitizer works with a direct `clang -fsanitize=thread`
  build.
- **`-fps_mode passthrough` matters for the reference.** Without it ffmpeg
  duplicates frames according to SEI timing (the JVT `CVSE2` stream), which
  looks like missing output. `CVSE3` and `CVSEFDFT3` duplicate frames even with
  it, so compare them after collapsing repeats in the reference.
- **Material**: x264 encodes of `testsrc2` and `mandelbrot` covering Baseline,
  Main and High at several sizes, slice counts, reference counts, QPs,
  deblocking settings, with and without CABAC, B frames, B pyramid, both direct
  modes, weighted P and B, the 8x8 transform and custom scaling matrices, plus
  the JVT conformance streams from
  `https://fate-suite.ffmpeg.org/h264-conformance/` (names in ffmpeg's
  `tests/fate/h264.mak`). Every progressive 4:2:0 8-bit conformance stream
  matches; the field, MBAFF, monochrome and high-bit-depth ones are out of
  scope, and `FM1_FT_E` stops at its first FMO slice.
- **Corrupt input**: flipping, overwriting and deleting random bytes of those
  streams, under UBSan, with and without threads, must neither crash nor hang.

On the device, a bench decodes a clip embedded at build time. It lives in a
separate build directory so the cache variables do not leak into normal
builds:

```sh
nix develop -c idf.py -C esp32p4 -B esp32p4/build-bench \
    -DH264_BENCH_CLIP=/path/to/clip.h264 -DH264_DEC_PROFILE=1 -p <port> flash
echo "settle
h264bench 3 hash
wait 30000" | nix develop -c ./esp-devkit/tools/harness/harness.py --port <port> --log --out captures
```

`h264bench <loops> [hash] [single] [show] [present] [fps=N]` runs in the
background and logs `H264:` lines: time per frame, cycles, and with
`H264_DEC_PROFILE` the share of each stage (the shares mix both cores, so
"rest" can go negative). `hash` prints `[H264V]` lines to diff against the host
tool; `single` runs without the post task; `show` decodes and draws through
`H264Renderer` in one loop; `present` goes through `video_presenter` at `fps`.
The command returns at once because the harness gives replies five seconds.

## Where the time goes

Device, dual-core, bit-exact with the host:

| clip | decode |
|---|---|
| 640x360 Baseline CAVLC, 0.13 Mbit/s | 21 ms (46 fps) |
| 640x360 High CABAC+B+8x8, same source | 36 ms (28 fps) |
| 640x360 High CABAC+B+8x8, `testsrc2` at CRF 23 | 45 ms (22 fps) |
| 1280x720 High CABAC+B+8x8 | 172 ms (6 fps) |

Main and High cost roughly 1.7x Baseline on the same material, and almost all
of it is motion compensation: for the High clip above, luma about a quarter,
chroma a fifth and filling the SRAM reference window another fifth, against one
per cent for CABAC. Bi-prediction is why — every B partition is predicted twice
and every fetch unpacks the packed DPB layout. The entropy coder, the transform
and intra prediction barely register.

The window does not pay for itself in B pictures (disabling it there measured
within two per cent), because only list 0 is windowed and the list 1 fetches go
to PSRAM anyway; it stays because P pictures do benefit.

**Keeping a planar copy of each reference next to the packed one does not help,
and it was measured.** The idea was to stop unpacking: write every reference
picture a second time as planes, so motion compensation reads them directly.
Both arrangements were tried on the device with the 360p High clip above, which
takes 35.5 ms per frame as it stands:

| arrangement | ms/frame |
|---|---|
| packed only, SRAM window (what is in the tree) | 35.5 |
| planar copy as well, window filled by `memcpy` | 38.9 |
| planar copy as well, no window, filters read PSRAM | 38.8 |

Motion compensation did get about 8 ms faster without the unpacking, but a
second copy of a 360p frame is 353 KB and writing it costs more than that at
this PSRAM bandwidth. The decoder is limited by PSRAM traffic, not by the
unpacking work, so any scheme that adds a whole-frame copy loses. For the same
reason a second window (list 1 at 360p, paid for by halving both) was not
pursued: a window fill costs a whole picture's worth of unpacking, more than the
on-demand list 1 fetches it would replace.
